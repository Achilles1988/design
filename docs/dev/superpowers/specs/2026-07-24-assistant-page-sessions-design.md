## AI 助手页面级会话与筛选持久化设计

- 日期：2026-07-24
- 状态：已批准，待实施计划
- 范围：`apps/design/framework`

## 背景

当前 `AssistantProvider` 挂载在 `SidebarShell`，整个应用共享一个
assistant-ui `LocalRuntime`。因此聊天会跨页面延续，而
`AssetBrowserPage` 的筛选仅保存在页面组件的 React state 中，离开页面后会被销毁。

现有 `apply_filter` 工具具备增量更新筛选的基础能力，但产品需要把“发送明确筛选需求后，
页面内容真实更新”作为完整交互契约验证，而不只验证工具函数本身。

本设计解决三个相关问题：

- AI 面板可以开始新聊天；
- 每个具体页面拥有独立聊天和页面状态，离开、刷新或重启后仍可恢复；
- 明确的筛选 prompt 在同一轮更新 chips、数量和资产内容。

## 已确认决策

| 主题 | 决策 |
|---|---|
| 新聊天语义 | 清空当前页面的聊天，不保留旧会话历史 |
| 新聊天与筛选 | 同时清空当前页面筛选，回到完整资产列表 |
| 持久化范围 | 使用浏览器本地存储，刷新或重启后恢复 |
| 页面隔离粒度 | 按具体页面地址隔离，不同 App 和 Canvas 分别独立 |
| AI 筛选行为 | 条件明确时必须同轮调用筛选工具；条件不足可追问；无关请求不改筛选 |
| Runtime 方案 | 保留单一 Shell 级 LocalRuntime，由页面会话协调器切换其当前状态 |
| 历史会话 | 不提供会话列表或旧会话切换 |

## 目标

- Rule、Layout、不同 App 和不同 Canvas 的聊天互不串联。
- 页面离开后再返回，或浏览器刷新、重启后，恢复该页面的聊天与可持久化业务状态。
- AI 和手动操作产生的筛选变化使用同一份页面状态。
- `New chat` 原子地清空当前页面聊天与筛选。
- 明确筛选需求通过 `apply_filter` 真实更新 chips、数量和资产列表。
- 页面切换时中止旧请求，避免迟到结果污染新页面。
- 不新增第三方依赖。

## 非目标

- 多会话历史、会话重命名或历史会话切换。
- 跨浏览器、跨设备或服务端同步。
- 本地缓存管理页面或用户可配置的保留期限。
- 新 AI provider、后端聊天端点或新的配置字段。
- 为当前尚未注册 AI 能力的页面新增 AI 工具。

## 方案选择

采用页面键控的单 Runtime 状态协调器。

继续保留 Shell 级 `AssistantProvider` 和当前单线程 UI。新增协调层，在页面改变时依次保存
旧页面、取消旧运行并恢复新页面。assistant-ui 当前版本提供线程快照、订阅和
`reset(initialMessages)`，足以在不引入多线程 UI 或额外依赖的前提下落地。

未选择的方案：

- 每个页面重新挂载独立 Runtime：隔离直观，但仍需持久化层，并增加 Provider 重挂载、
  工具重新注册和面板状态衔接的复杂度。
- assistant-ui 多线程模型：适合可见的历史会话产品，但会把页面身份和聊天线程概念混合，
  超出当前单会话需求。

## 架构

### `AssistantPageStateStore`

提供纯粹的页面状态持久化能力：

- 从页面键读取并校验状态；
- 写入版本化、JSON 可序列化的状态；
- 删除单个页面状态；
- 对无效版本、损坏 JSON 和不合法字段安全降级；
- 对存储不可用或容量不足返回可处理的结果，不阻断内存中的当前会话。

状态结构定义为：

```ts
type AssistantPageStateV1 = {
  version: 1
  messages: PersistedMessage[]
  filter?: Filter
  updatedAt: string
}
```

`PersistedMessage` 只保存恢复对话和模型上下文所需的稳定字段，包括角色、文本、工具调用与
已完成工具结果。运行中状态、临时错误对象、函数和不可序列化值不得写入本地存储。

本地存储使用一个带版本的命名空间键，内部以 `pageKey` 索引，避免为任意路径创建大量顶层
key。写入时保留其他页面状态。

### 页面键

页面键由规范化地址生成：

- pathname 保留具体路由参数，因此 `/apps/a` 与 `/apps/b` 不同；
- Canvas 路径保留 App ID 和 Canvas ID；
- 查询参数仅纳入会影响页面业务上下文的白名单字段，并按名称和值稳定排序；
- hash、面板开合、临时选择和其他纯 UI 状态不纳入；
- Rule 与 Layout 自然形成不同页面键。

当前资产页的 `appId` 会影响页面上下文，应纳入白名单。后续页面增加影响 AI 上下文的查询
参数时，必须显式登记，不能默认把所有临时参数写入页面键。

### `AssistantPageSessionCoordinator`

协调器位于 Shell 级 `AssistantProvider` 内，负责使单一 Runtime 始终对应当前页面：

- 订阅当前 Runtime 的稳定消息变化并保存到当前页面；
- 页面键变化时，取消旧页面仍在进行的生成或工具调用；
- 保存旧页面最后一个稳定快照；
- 从 Store 加载新页面消息；
- 使用 `thread.reset(restoredMessages)` 装载新页面会话；
- 使用切换代次或当前页面令牌忽略迟到的异步结果；
- 向 AI 面板暴露当前页面是否有状态以及 `startNewChat()`。

恢复期间必须阻止自动保存空 Runtime 覆盖已持久化的新页面状态。协调器要明确区分
“切换中”和“已激活”阶段，完成导入后才能恢复订阅写入。

### `usePageAssistant`

保留现有 instructions 和 availability 注册，并扩展一个稳定的页面状态重置回调：

```ts
usePageAssistant({
  instructions,
  available,
  onResetPageState,
})
```

协调器负责通用聊天，页面仍拥有业务状态。`onResetPageState` 让 `New chat` 在不耦合
`AssistantThread` 与资产筛选实现的前提下清空当前页面业务状态。

该公共契约的新增参数和生命周期语义必须同步更新
`docs/dev/api/assistant-ui-chat.md`。

### `AssetBrowserPage`

资产页负责筛选业务状态：

- 首次进入时从当前页面状态恢复 `filter`；
- 恢复的 chip 需通过当前资产索引校验；
- AI、手动删除 chip 和 `Reset all` 都更新同一份 React state；
- 每次稳定筛选变化写入当前页面状态；
- `onResetPageState` 同步清空 `filterRef` 和 React state；
- instructions 始终由最新 filter 和候选集合重新构建。

聊天消息与筛选必须落在同一个 `pageKey` 下，不能分别使用不同的页面身份算法。

## 新聊天交互

AI 面板标题栏增加英文 `New chat` 操作，位于关闭按钮左侧，并遵循现有 dashboard token、
交互状态和窄屏布局。

当前聊天或筛选非空时，点击后使用现有确认提示：

> Start a new chat? This clears the conversation and filters for this page.

页面状态为空时可直接保持空状态并聚焦输入框，不显示无意义确认。

确认后按以下顺序完成一次新聊天：

1. 取消当前生成和工具执行；
2. 使旧异步结果失效；
3. 重置 Runtime 消息；
4. 调用当前页面的业务状态重置回调；
5. 删除当前页面的持久化状态；
6. chips、数量和资产列表恢复为完整列表；
7. 输入框获得焦点。

从用户观察角度，最终状态必须是“空聊天、空筛选”。任何中间步骤失败都不能让刷新后恢复
出旧聊天或旧筛选。

## AI 筛选数据流

明确筛选需求继续采用工具驱动，不从助手文本解析筛选：

```text
用户 prompt
  → 模型根据最新 instructions 判断条件明确
  → 调用 apply_filter 增量工具
  → execute 从最新 filterRef 合并 delta
  → 同步更新 filterRef 和 React state
  → chips、数量、资产列表在同一轮刷新
  → 页面筛选状态持久化
  → 工具结果回传模型
  → 模型基于真实 applied delta 和 matchCount 生成摘要
```

行为边界：

- prompt 含可执行的明确条件时，系统提示要求模型调用 `apply_filter`；
- 条件不足时可以先追问；
- 无关请求礼貌拒绝且不调用工具；
- 普通文本回复不改变筛选；
- 空 delta 不声称筛选发生变化；
- 工具失败保留原筛选，并返回结构化失败结果；
- 后续轮次始终获得最新筛选和当前候选集合。

不能只用 `applyFilterExecute` 的函数测试证明功能完成。必须覆盖从 composer 发送消息、
adapter 转发工具、工具执行到资产页面重新渲染的集成链路。

## 页面切换与并发

页面键发生变化时：

1. 标记旧页面会话不再是当前目标；
2. 取消正在运行的模型请求；
3. 保存旧页面最后一个稳定状态；
4. 装载新页面持久化状态；
5. 页面工具和 instructions 完成注册后才允许发送新消息。

如果旧请求在取消后仍返回数据，其页面令牌与当前令牌不匹配，结果必须被忽略。旧页面的
工具不得操作新页面的筛选引用。

AI 面板的开合可以继续由 Shell 保存；页面切换不要求自动关闭面板。面板保持打开时应直接
显示新页面对应的聊天，不短暂展示旧页面内容。

## 错误处理

- JSON 损坏、版本不支持或消息结构无效：仅丢弃对应页面的无效缓存，并以空状态继续。
- 本地存储读取被浏览器拒绝：以当前内存状态运行。
- 写入失败或容量不足：保留内存状态，并显示非阻塞、英文的持久化失败提示。
- 恢复的筛选项不再适用于当前资产索引：移除无效项，并写回修正后的状态。
- 工具执行失败：恢复 `filterRef`，不改变页面筛选，不写入错误状态。
- 页面切换和新聊天：取消运行并以页面令牌防止迟到结果写入。
- 新聊天清理失败：再次以空状态覆盖当前页面存储，确保最终一致。

## 测试策略

### 状态存储

- 相同地址生成稳定页面键；
- 不同 Rule、Layout、App 和 Canvas 生成不同页面键；
- 查询参数白名单与稳定排序；
- 状态读写、更新单页和删除单页；
- 损坏 JSON、未知版本和非法消息安全降级；
- localStorage 不可用和容量不足。

### 会话协调

- 离开页面时保存，返回时恢复；
- 刷新初始化时恢复当前页面；
- 页面切换不会先用空 Runtime 覆盖目标缓存；
- 切页取消运行并忽略迟到结果；
- 不同 App、Canvas、Rule 和 Layout 不共享消息；
- 新聊天重置消息并删除当前页面状态；
- 其他页面状态不受新聊天影响。

### 资产筛选

- AI 工具变化、手动删除 chip 和 `Reset all` 均持久化；
- 离开并返回资产页后恢复 chips、数量和可见资产；
- 刷新后恢复同一筛选；
- 无效的历史 chip 被清理；
- 新聊天同时清空聊天、filter state 和 `filterRef`；
- 新聊天后刷新不会恢复旧筛选。

### 完整 AI 链路

- 输入含明确条件的 prompt 后，adapter 提供可执行的 `apply_filter`；
- 工具调用更新 chips、匹配数量和左侧资产内容；
- 连续多轮基于最新筛选累积和移除条件；
- 无工具调用的回复不改变筛选；
- 空 delta 与工具失败不显示误导性成功状态；
- Rule 与 Layout 来回切换时，各自恢复聊天与筛选。

### 验证

- 运行相关单元和组件测试；
- 运行完整 `npm run test`；
- 运行生产构建；
- 在桌面和窄屏、明暗主题下进行浏览器冒烟测试；
- 检查 `New chat` 的键盘操作、焦点恢复、确认提示与请求中断。

## 验收标准

- 每个具体页面地址拥有独立聊天，不出现跨页面消息。
- 不同 App 和 Canvas 分别恢复自己的聊天。
- Rule 与 Layout 分别恢复自己的聊天与筛选。
- 离开页面、刷新或重启浏览器后可以恢复状态。
- `New chat` 清空当前页面聊天与筛选，但不影响其他页面。
- 明确筛选 prompt 在同一轮真实改变 chips、数量和资产内容。
- 条件不足或无关请求不会误改筛选。
- 页面切换或新聊天期间的迟到结果不会污染当前页面。
- 持久化损坏或不可用时，应用仍可在内存模式正常使用。
- 完整测试套件和生产构建通过。
